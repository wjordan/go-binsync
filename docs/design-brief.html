Design brief · 2026-08-26 · design phase: codec prototyped and measured, no product code yet

binsync ships an incremental release of a 94 MB Go server as 0.11 MB — encoded in two seconds, across a lossy 20 Mbit/s link in one.

Software often needs to fly across the world: a fleet of servers all running one large, monolithic Go binary, rebuilt many times a day, reached over links where packet loss and congestion turn a big download into a crawl. The way out is to ship only what changed. binsync is an experiment in pushing that further than a compressed archive, a content-defined-chunk store or a general binary diff can go, using the idea behind Google's Courgette: read the structure the compiler left behind and predict where everything moved, instead of diffing bytes. A stripped Go binary still carries its function table; binsync aligns old and new release by function name, predicts the new layout, and sends only the correction — then installs the verified result and re-execs the service with its sockets handed over. This page condenses README.md, docs/DESIGN.md and docs/research/.

The performance profile

One real incremental release — prometheus 3.13.1 → 3.13.2, a 94 MB stripped linux/amd64 binary built with Go 1.27 — encoded once by the publisher and fetched by a target over a medium-quality link: 20 Mbit/s, 200 ms RTT, 1 % packet loss. Three numbers decide how fast a release lands: encoder cost, bytes on the wire, and what those bytes cost on the link.

The encoder is faster than the generic tools because it never builds a suffix array over the file. What is still the prototype's is memory: encoder and decoder hold old, predicted and new in RAM (≈ 7× the file); working section by section brings that to ≈ 2×. The same codec turns a one-line change of a 30 MB binary into 2.2 KB (bsdiff 150 KB) and a multi-package edit into 2.7 KB (bsdiff 145 KB); on a minor release that adds thousands of functions the gain drops to 1.6×, which is the correct result — the codec removes layout churn, and cannot remove code.

Why the ladder looks like this: a Go code change that grows one function by a few bytes shifts every later function and rewrites every reference that crosses the shift, so the file changes almost everywhere while almost nothing changed. Whole-file compressors and chunk stores see only bytes — a one-liner rewrites 13 % of them and a real release 79–87 %, in runs a few bytes long, so no chunk survives and a chunk store re-sends more than a fresh archive. Exact-match delta coders (zstd --patch-from, xdelta3) find the moved code but pay for every shifted operand. Approximate matchers (bsdiff, hdiffz) absorb the shifted operands as cheap byte differences and are several times better, at the price of a suffix array over the whole file. binsync reads the function table the Go linker leaves in a stripped binary and predicts the shift instead of encoding it. Go 1.27 makes the gap wider: its new sorted type-descriptor section is full of code offsets, which makes generic deltas of a one-liner 2.5× larger than on Go 1.26 and leaves binsync's patch unchanged.

Predict, then correct

A stripped Go binary keeps .gopclntab — every function's name, entry and size — plus moduledata and the type tables. That is enough for the decoder to rebuild the new binary's layout from the old one: match functions by name, move each body to its new address, re-target every PC-relative operand (x86 decode via x/arch), re-lay data blocks through shift maps, regenerate the offset-based pclntab with its pc tables, and the type descriptors. The patch carries the new layout (a few KB) plus a positional correction of whatever the prediction got wrong. Prediction only has to be deterministic, not right: the decoder hashes the predicted base and the result, so a bad guess costs bytes, never correctness.

old binary ─┬─ parse pclntab (names, entries, sizes) ─▶ match by name ─▶ layout table + data maps   ← sent (0.4–6 KB)
            ├─ .text: copy matched bodies to new entries, relocate rip-rel/rel32 operands

Every row is encode → patch → decode → byte-exact compare, with all tables counted in the patch. What the prometheus patch still carries: the changed code itself (63 KB of 112 KB), 45 KB of type descriptors (two-thirds genuinely new ones), and the pc tables of the functions that changed (14 KB); layout tables are 11 KB. A hdiffz correction stage instead of positional runs gets it to 94 KB, which bounds what a local approximate match inside changed functions can add. Unsupported inputs (non-Go, arm64, PIE, a Go release the deployed decoder does not know) fall back to a plain bsdiff-class codec up to 256 MB, or to the full blob — never to a failure.

Decisions

D1–D3
Delta patches; Go-aware predict-then-correct as the codec; positional correction after a layout-exact prediction.CDC/CAS re-sends ~100 %; bsdiff cannot scale to 1 GB (9–12× RAM, minutes); function-name alignment from pclntab removes the layout churn and the need for a suffix array. Plain bsdiff-class fallback (≤ 256 MB) for anything the transform cannot parse.
D4–D5
One mutable pointer, immutable content-addressed objects, a chain of prev → head patches, 8 MiB hashed frames.One conditional GET to poll; CAS on the pointer prevents forks; a target ≤ 8 releases behind follows the chain, otherwise takes the blob; frames give parallel ranged fetch (S3/GCS have no multi-range) and resume.
D6
No signing key. Authenticity from the endpoint (TLS, SigV4, SSH, local fs); integrity from BLAKE3 hashes reachable from the pointer; replay protection from a monotonic seq.Same trust model as go install and registries; a signature can be added as a pointer field later without changing the layout.
D7–D10
Two hooks (--restart, --healthy) or two calls (Ready(), OnShutdown); same-socket fd inheritance run by the old process; hardlink + rename install; exec by path.Three outcomes per update — ready, reverted, or failed-and-skipped — with no state machine or probation window. Sharing one accept queue is the only loss-free handoff on every kernel (SO_REUSEPORT drops connections below 5.14); /proc/self/exe is the old inode after a rename.
D11–D12
-s -w required; poll only.DWARF makes every patch ≈ a full download; a 304 costs one RTT and the workstation case is file:// polled at 1 s. No signing keys, control socket, inline patches, direct edges, channels, or systemd-notify.
D13
Publish order: patch → pointer → blob. A blob that is still uploading is retried, not an error.Every steady-state target needs only the patch, so the pointer goes live after hundreds of KB instead of tens of MB — from a workstation over one lossy SSH stream that is seconds instead of minutes. Drifted targets that 404 on the blob back off and are healed by the next publish.
D14
The Go-aware codec targets the current stable Go release (1.27) only; other toolchains get the plain codec.pclntab and type-descriptor layouts change between Go minors; one supported version, gated by a byte-exact self-prediction check of the old binary, keeps the codec small and honest. The publisher picks the transform the deployed decoder can read.

How an update runs

<store>/latest.json               { seq, head {hash, version, size, blob}, chain [{from, to, key, size, b3} …] }   no-store
<store>/patches/<from>-<to>.bsz   transform id, layout tables, correction; 8 MiB hashed frames                  immutable
<store>/blobs/<hash>.zst          full binary in independent 8 MiB zstd frames (parallel ranged fetch)           immutable

publish:  hash · encode vs previous head (local cache) · put patch → pointer (If-Match CAS) → blob frames
agent:    GET latest.json (If-None-Match) ──304──▶ sleep
                                         ──200──▶ seq ↑ ▶ hash current file (cached by inode) ▶ chain suffix or blob
                                                  ▶ fetch frames (verify each) ▶ apply ▶ verify b3 ▶ install ▶ restart ▶ ready | revert

install:  write <path>.tmp (fsync, verify b3) · link(<path>, <path>.old) · create <path>.pending · rename(tmp, <path>) · fsync(dir)
embedded: old process execs <path> with listeners as inherited fds
          ├─ child calls Ready()   → child unlinks .pending; old stops accepting, runs OnShutdown (drain ≤ 30 s), exits
          └─ child exits / 60 s    → SIGTERM…SIGKILL; rename(.old, <path>); record failed; old keeps serving
external: run --restart CMD → [--healthy URL|CMD until 60 s] → ok: unlink .pending · not ok: revert, restart again, record failed
any start: .pending exists ∧ not launched by a parent ∧ .old exists → revert, record failed, exec <path>

Invariants

  • <path> is byte-for-byte the head release once visible, and a valid executable at every instant.
  • Nothing queued on a listening socket is lost: both processes accept until Ready().
  • One update in flight per target; a reverted release is skipped until the pointer changes.

What the user writes

up := selfupdate.Start(selfupdate.Config{Store: "s3://b/releases/app"})
ln, _ := up.Listen("tcp", ":8080")
up.OnShutdown(func() { srv.Shutdown(ctx) })
go srv.Serve(ln)
up.Ready()
<-up.Done()

Or, without linking: binsync agent s3://b/releases/app /srv/app --restart 'systemctl restart app' --healthy http://127.0.0.1:8080/healthz. Build releases with CGO_ENABLED=0 go build -trimpath -buildvcs=false -ldflags="-s -w -buildid=".

Not in v1: signed manifests, push notifications, channels, direct patches, arm64/PIE/older-toolchain Go-aware codec (plain codec meanwhile), Windows, multi-file bundles, P2P fan-out. Sources: README.md · docs/DESIGN.md · docs/research/ · prototype bench/gotransform/.
