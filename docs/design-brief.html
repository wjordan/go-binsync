Design brief · rev 2 · 2026-08-27 implemented · deployed · measured

A one-line change to a 30 MB Go binary ships as 2,262 bytes — 67× smaller than bsdiff. A real 94 MB release ships as 0.095 MB.

Software often needs to fly across the world: a fleet of servers all running one large, monolithic Go binary, rebuilt many times a day, reached over links where packet loss and congestion turn a big download into a crawl. The way out is to ship only what changed. binsync pushes that further than a compressed archive, a content-defined-chunk store or a general binary diff can go, using the idea behind Google's Courgette: read the structure the compiler left behind and predict where everything moved, instead of diffing bytes. A stripped Go binary still carries its function table; binsync aligns old and new release by function name, predicts the new layout, and sends only the correction — then installs the verified result and re-execs the service with its sockets handed over. This page condenses README.md, docs/DESIGN.md, docs/DEMO.md and docs/research/; the library, CLI, agent and public demo are built, and every number on it is measured on them.

The headline number

One string literal changed in one handler of a 30 MB Go service. Nothing else in the source moved — but the linker moved 13 % of the bytes in the file, because every function after the edit shifted and every reference that crossed the shift was rewritten. That is what a byte-level differ has to encode, and what a Go-aware one can predict.

The performance profile

The synthetic pair above isolates the effect. A real incremental release — prometheus 3.13.1 → 3.13.2, a 94 MB stripped linux/amd64 binary built with Go 1.27 — carries genuinely new code as well, and is the honest case: encoded once by the publisher, fetched by a target over a medium-quality link of 20 Mbit/s, 200 ms RTT, 1 % packet loss.

The encoder is faster than the generic tools because it never builds a suffix array over the file. The number still out of place is memory: the decoder peaks at 714 MB of live heap for a 94 MB binary — 7.6×, and only 2× of that is the file buffers — the rest is the prediction's own working set. A 1 GB binary at that ratio asks a target for 7.6 GB, which is not a thing a fleet can be asked for. Getting it to ≈ 2× is the one open constraint, and none of the three fixes it needs changes the patch format. The other honest limit is the one the codec cannot argue with: on a minor release that adds thousands of new functions the gain falls to 1.6×, which is the correct result — binsync removes layout churn, and cannot remove code.

Why the ladder looks like this: a Go code change that grows one function by a few bytes shifts every later function and rewrites every reference that crosses the shift, so the file changes almost everywhere while almost nothing changed. Whole-file compressors and chunk stores see only bytes — a one-liner rewrites 13 % of them and a real release 79–87 %, in runs a few bytes long, so no chunk survives and a chunk store re-sends more than a fresh archive. Exact-match delta coders (zstd --patch-from, xdelta3) find the moved code but pay for every shifted operand. Approximate matchers (bsdiff, hdiffz) absorb the shifted operands as cheap byte differences and are several times better, at the price of a suffix array over the whole file. binsync reads the function table the Go linker leaves in a stripped binary and predicts the shift instead of encoding it. Go 1.27 makes the gap wider: its new sorted type-descriptor section is full of code offsets, which makes generic deltas of a one-liner 2.5× larger than on Go 1.26 and leaves binsync's patch unchanged.

Predict, then correct

A stripped Go binary keeps .gopclntab — every function's name, entry and size — plus moduledata and the type tables. That is enough for the decoder to rebuild the new binary's layout from the old one: match functions by name, move each body to its new address, re-target every PC-relative operand (x86 decode via x/arch), re-lay data blocks through shift maps, regenerate the offset-based pclntab with its pc tables, and the type descriptors. The patch carries the new layout (a few KB) plus a positional correction of whatever the prediction got wrong. Prediction only has to be deterministic, not right: the decoder hashes the predicted base and the result, so a bad guess costs bytes, never correctness.

old binary ─┬─ parse pclntab (names, entries, sizes) ─▶ match by name ─▶ layout table + data maps   ← sent (0.4–10 KB)

Every row is encode → patch → decode → byte-exact compare, with all tables counted in the patch. The prediction of the 94 MB release is wrong in 120,852 bytes — 0.13 % of the file. What the patch carries: the changed code itself (63,179 B), type descriptors (45,170 B, two-thirds of them genuinely new), the pc tables of the functions that changed (17,441 B compressed) and the layout tables (10,379 B compressed). That is 1 % above the 94,470 B a hdiffz correction stage reaches, which bounds what a better local match inside changed regions could still add. Unsupported inputs (non-Go, arm64, PIE, a Go release the deployed decoder does not know) fall back to a plain bsdiff-class codec up to 256 MB, or to the full blob — never to a failure.

Decisions from the design phase

D1–D3
Delta patches; Go-aware predict-then-correct as the codec; positional correction after a layout-exact prediction.CDC/CAS re-sends ~100 %; bsdiff cannot scale to 1 GB (9–12× RAM, minutes); function-name alignment from pclntab removes the layout churn and the need for a suffix array. Plain bsdiff-class fallback (≤ 256 MB) for anything the transform cannot parse.
D4–D5
One mutable pointer, immutable content-addressed objects, a chain of prev → head patches, 8 MiB hashed frames.One conditional GET to poll; CAS on the pointer prevents forks; a target ≤ 8 releases behind follows the chain, otherwise takes the blob; frames give parallel ranged fetch (S3/GCS have no multi-range) and resume.
D6
No signing key. Authenticity from the endpoint (TLS, SigV4, SSH, local fs); integrity from BLAKE3 hashes reachable from the pointer; replay protection from a monotonic seq.Same trust model as go install and registries; a signature can be added as a pointer field later without changing the layout.
D7–D10
Two hooks (--restart, --healthy) or two calls (Ready(), OnShutdown); same-socket fd inheritance run by the old process; hardlink + rename install; exec by path.Three outcomes per update — ready, reverted, or failed-and-skipped — with no state machine or probation window. Sharing one accept queue is the only loss-free handoff on every kernel (SO_REUSEPORT drops connections below 5.14); /proc/self/exe is the old inode after a rename.
D11–D12
-s -w required; poll only.DWARF makes every patch ≈ a full download; a 304 costs one RTT and the workstation case is file:// polled at 1 s. No signing keys, control socket, inline patches, direct edges, channels, or systemd-notify.
D13
Publish order: patch → pointer → blob. A blob that is still uploading is retried, not an error.Every steady-state target needs only the patch, so the pointer goes live after hundreds of KB instead of tens of MB — from a workstation over one lossy SSH stream that is seconds instead of minutes. Drifted targets that 404 on the blob back off and are healed by the next publish.
D14
The Go-aware codec targets the current stable Go release (1.27) only; other toolchains get the plain codec.pclntab and type-descriptor layouts change between Go minors; one supported version, gated by a byte-exact self-prediction check of the old binary, keeps the codec small and honest. The publisher picks the transform the deployed decoder can read.

What building it decided

Eight decisions the design phase could not make, because each of them needed a working encoder and a number. They are the difference between the 111,552 B the prototype reached on the real pair and the 95,366 B the implementation does.

D15
A correction region is written as literals or as a bounded local match, whichever is smaller.Recovers the bsdiff-quality bytes inside changed functions that purely positional runs re-send, at O(region) memory — and lets the decoder apply the correction in place, which removed a whole copy of the file from the decoder's heap.
D16 · D22
Every stream takes the smaller of zstd and brotli — and blob frames turned out to be brotli-10, not zstd.Pure-Go zstd is 6–14 % worse than the zstd -19 CLI the research numbers were taken with; pure-Go brotli is better at both qualities. In 8 MiB frames, brotli-10 is 15 % smaller than the zstd blob and smaller than a single zstd -19 stream of the whole file, which the frame split was expected to cost against: 13 s of publisher CPU and 269 ms of target CPU. Each frame carries its own codec tag, so a blob is not a file any single decompressor reads — hence blobs/<hash>.blob, not .zst.
D17
The pc-table stages use the plain codec, not the positional correction.Their residual is shifted, not positional: one pc table that changed length moves every table after it. Positionally that stage costs 66,372 B on the real pair against 17,441 B — 51 KB, more than half the finished patch.
D18 · D19
The source window of a correction region is derived, not transmitted; the patch body is one frame per 8 MiB, not one frame per stream.Both sides know the region's end and the file's length, and there are tens of thousands of regions at 2–4 varints each. Compressing the streams separately came within 0.1 % of compressing them together, so frames are cut for resumability instead.
D20
The encoder transmits the BLAKE3 of its own prediction, and every worker count is a compile-time constant.A prediction that varies with GOMAXPROCS is one two hosts can disagree about. With the hash in the patch, encoder/decoder divergence is a named failure and a blob fallback instead of a wrong file that the release hash happens to catch.
D21
The prediction fills the bytes no allocated section covers: gaps cleared, .shstrtab copied from the old file's tail.The predicted base starts as a copy of the old file, so every section that moved left stale bytes behind in its gap — 3,780 mispredicted bytes on the real pair, 109 after.

How an update runs

<store>/latest.json               { seq, head {hash, version, size, blob}, chain [{from, to, key, size, b3} …] }   no-store
<store>/patches/<from>-<to>.bsz   transform id, layout tables, correction; 8 MiB hashed frames                  immutable
<store>/blobs/<hash>.blob         full binary in independent 8 MiB frames, brotli or zstd per frame            immutable

publish:  hash · encode vs previous head (local cache) · put patch → pointer (If-Match CAS) → blob frames
agent:    GET latest.json (If-None-Match) ──304──▶ sleep
                                         ──200──▶ seq ↑ ▶ hash current file (cached by inode) ▶ chain suffix or blob
                                                  ▶ fetch frames (verify each) ▶ apply ▶ verify b3 ▶ install ▶ restart ▶ ready | revert

install:  write <path>.tmp (fsync, verify b3) · link(<path>, <path>.old) · create <path>.pending · rename(tmp, <path>) · fsync(dir)
embedded: old process execs <path> with listeners as inherited fds
          ├─ child calls Ready()   → child unlinks .pending; old stops accepting, runs OnShutdown (drain ≤ 30 s), exits
          └─ child exits / 60 s    → SIGTERM…SIGKILL; rename(.old, <path>); record failed; old keeps serving
external: run --restart CMD → [--healthy URL|CMD until 60 s] → ok: unlink .pending · not ok: revert, restart again, record failed
any start: .pending exists ∧ not launched by a parent ∧ .old exists → revert, record failed, exec <path>

Invariants

  • <path> is byte-for-byte the head release once visible, and a valid executable at every instant.
  • Nothing queued on a listening socket is lost: both processes accept until Ready().
  • One update in flight per target; a reverted release is skipped until the pointer changes.

Or, without linking: binsync agent s3://b/releases/app /srv/app --restart 'systemctl restart app' --healthy http://127.0.0.1:8080/healthz. Build releases with CGO_ENABLED=0 go build -trimpath -buildvcs=false -ldflags="-s -w -buildid=".

Open: the decoder's 7.6× memory footprint (§11.3), the .go.type residual, arm64. Not in v1: signed manifests, push notifications, channels, direct patches, arm64/PIE/older-toolchain Go-aware codec (plain codec meanwhile), Windows, multi-file bundles, P2P fan-out.
