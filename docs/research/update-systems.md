# Update / artifact-distribution systems: transport, storage, fan-out and latency

Research notes for go-binsync (2026-08-26). Scope: the *system* level of existing
software-update and artifact-distribution designs - how a release is described,
how a target discovers it, how the server decides which patch to serve, how many
"from" versions are kept, how fallback and drift are handled, and what the hot
path costs in round trips. The diff algorithm itself is out of scope.

Sourcing rule: every number below has an inline URL to a primary source unless
marked *(secondary)*. Where a number could not be found it says so rather than
guessing. Numbers quoted from search snippets of pages that would not render
are marked *(snippet)*.

---

## 1. Summary of findings

1. **Only Windows UUP solves "any from-version to latest" with O(1) artifacts per release.** Each changed file ships as (reverse delta N->RTM, forward delta RTM->N); a client on any revision reverts to the common base then goes forward. Express updates (the predecessor) kept per-file deltas from ~5 historical baselines at 150-200 MB per patch set and needed byte-range servers; UUP pairs cost "roughly 250MB" server-side and download "less than double" an Express update, with 40% less client memory because no inventory pass is needed. (Microsoft Learn; Raymond Chen.)
2. **Everyone else uses an explicit (from, to) patch matrix with a small K, or CDC chunk reuse.** Firefox: partials from the last 4 shipped releases + last beta for RCs; deltas only served on an *exact buildID match*, else complete. Chrome: server matches the client-reported SHA-256 fingerprint; depth is undocumented. ostree/Flatpak: parent + from-scratch by default, "full permutation ... can get expensive". deltarpm: 1 prior version, available ~1 day - dropped in Fedora 40 after measuring 8% average savings and 52.7 MB average waste on failures.
3. **CDC chunk systems (Steam, zchunk, casync/desync/bita, Riot, zstd:chunked) have no patch matrix at all**: any local bytes are a seed. The cost moves to round trips: one GET per missing chunk (casync/desync, Steam) unless the client coalesces ranges (zchunk: up to 256 ranges per multipart request; bita: adjacent chunks per request; Riot: whole-bundle GET or multipart ranges over 8 HTTP/1.1 connections).
4. **Object storage does not support multi-range GET.** S3: "Amazon S3 doesn't support retrieving multiple ranges of data per GET request." GCS XML API: "Multiple byte ranges in a single request are not accepted." R2: undocumented. GHCR returned 501 to a 2-range request in a live test. Any zchunk/zstd:chunked-style multipart strategy therefore degrades to k requests on S3/GCS, so the *producer* must lay bytes out contiguously.
5. **S3 first-byte latency is ~30 ms in-region median, "100-200 ms" by AWS's own envelope, plus ~20 ms/MiB on one connection with a ~85-95 MB/s per-connection ceiling.** AWS: 8-16 MB ranges, one request per 85-90 MB/s desired. VLDB'23 (Durner et al.): median base latency ~30 ms, ~20 ms/MiB, per-request bandwidth clustered at 55-60 MiB/s with a hard ceiling near 95 MiB/s. S3 REST is HTTP/1.1 only (h2 preface gets 400); GCS supports HTTP/2 and 3.
6. **A conditional GET on a single tiny pointer object is the cheapest possible poll**: `If-None-Match` -> 304, no egress, billed as one GET ($0.0004/1000 on S3, $0.00036/1000 on R2, 304s "charged existing rates ... including for failed requests"). No object store has a watch/long-poll primitive; S3 event notifications are "typically ... delivered in seconds but can sometimes take a minute or longer" and only go to SNS/SQS/Lambda/EventBridge.
7. **S3 now supports compare-and-swap on the pointer**: `If-None-Match: *` on PUT since 2024-08-20, ETag `If-Match` on PUT since 2024-11-25; strong read-after-write since 2020-12-01. GCS has generation preconditions; R2 supports If-Match/If-None-Match on PUT via the S3 API.
8. **Round-trip budget at 100 ms RTT**: cold TCP+TLS1.3 = 2 RTT; HEAD+GET = 4 RTT (~460 ms); one conditional GET = 3 RTT (~330 ms); warm conditional GET = 1 RTT. A cold SSH session is ~6-8 RTTs before the command starts (SSH3 paper, Fig. 1), ~1-2 with ControlMaster. TUF's canonical client flow is 4 GETs minimum (timestamp -> snapshot -> targets -> target).
9. **Block-matching (rsync/zsync/Octodiff/wharf pass 1) is the wrong delta for rebuilt executables.** bsdiff paper: "a one-line source code patch in a 500kB executable could translate into a 50kB patch file" with naive diffs; Xdelta 5.2x vs bsdiff 11.6x on feature updates, 11.0x vs 58.3x on security updates. wharf's own data: two 82 MiB builds -> rsync patch 33 MiB vs bsdiff 174 KiB. Every production system that ships executables (Chrome, Firefox, Android, Windows, ostree, wharf rediff, Blizzard ZBSDIFF1) uses a bsdiff-class or pointer-aware algorithm.
10. **Every exact-base patcher hashes the base before applying, or fails late.** Android: per-op `src_sha256_hash`, "fail the OTA immediately and don't write anything" on mismatch. Firefox: per-file size+CRC precheck, mismatch -> complete MAR. Squirrel: `.shasum` check after bspatch. `inconshreveable/go-update` never hashes the base - it only checksums the result, so drift is discovered after doing all the patch work.
11. **Hashing cost is not negligible at a 100 ms budget.** 100 MB at SHA-256 without SHA-NI (~484 MiB/s) is ~200 ms; Go SHA-NI "3-4x" faster (Go 1.21 notes); Go BLAKE3 ports reach ~4 GB/s single-thread (lukechampine 4034 MB/s AVX-512, zeebo 4.00 GB/s AVX2), not the 6.9 GB/s Rust figure; xxh3 25-149 GB/s. Cache the base hash on the target.
12. **The only production Go-binary deploy tools do full copies.** gokrazy streams whole root/boot images with no compression or delta; Kamal/fly/Capistrano move OCI images or git trees; `sup`/`imployer` tar over SSH. The common `rsync -avz bin && ssh systemctl restart` pattern works only because rsync writes a temp file and renames (`--inplace` is documented as unsafe for in-use binaries).
13. **P2P fan-out only pays at thousands of hosts.** Kraken: 3 GB to 2,600 hosts p50 10 s / p99 18 s; Spegel: 17 GB image on 56 GPU nodes median 348 s -> 307 s (~12%), and its DHT lookup has a 20 ms timeout with fallback to upstream. Below ~1000 hosts, request/egress cost is irrelevant (1000 hosts polling every 60 s ~ $0.58/day on S3) and the workstation uplink or the per-host RTT budget dominates.
14. **Riot's League patcher is the closest analogue to what go-binsync wants on the transport side**: 64 KB FastCDC chunks, zstd-19 per chunk, >300,000 chunks packed into <5,000 content-addressed bundles, >85% bundle reuse between versions, ~8 MB signed FlatBuffers manifest, 8 HTTP/1.1 connections, whole-bundle GET or multipart ranges; patch time >8 min -> <40 s even though bytes went *up* (68 MB -> 83 MB) versus their prior bsdiff chain. Latency was won on round trips and parallelism, not bytes.
15. **rsync's block size for a 50 MB file is ~7 KB** (sqrt(len), rounded to 8, clamped to [700 B, 128 KiB] - verified in upstream `rsync.h`); wharf uses 64 KiB, Octodiff 2 KiB, zsync 2-4 KiB, casync/desync/bita/Riot/zstd:chunked ~64 KiB average CDC.

## 2. Delta-update systems and their release/metadata model

### 2.1 Google Omaha / Chrome

- **Delta method.** Courgette (2009): disassemble -> adjust pointers -> bsdiff. Canonical numbers (Chrome dev 190.1 -> 190.4): full 10,385,920 B, bsdiff 704,512 B, Courgette 78,848 B (https://www.chromium.org/developers/design-documents/software-updates-courgette/). Zucchini replaced it for Chrome patching (PE/ELF/DEX; ~15-20 min and ~1 GB RAM to generate for Chrome; "fallback for direct downloads if patching fails") (https://chromium.googlesource.com/chromium/src/+/main/components/zucchini/README.md). No Google-published Zucchini-vs-Courgette sizes exist; Mozilla's mbsdiff->Zucchini numbers are the best proxy (section 2.2).
- **Metadata.** Protocol v3: client POSTs XML with `<package fp="1.<sha256>">`; response `<package name namediff size sizediff hash_sha256 hashdiff_sha256 fp>` and `<url codebase codebasediff>` (https://github.com/google/omaha/blob/main/doc/ServerProtocolV3.md). Protocol 3.1: "A version number is usually insufficient to identify the binaries the client already has ... the server sends a more precise label ... called a 'differential fingerprint'"; "Clients should attempt a differential patch of package first, and fall back to a full package if the differential patch fails" (https://chromium.googlesource.com/chromium/src/+/main/docs/updater/protocol_3_1.md). Protocol 4: request carries `cached_items` (SHA-256 list); response is ordered `pipelines` of ops (`download`, `xz`, `zucc`, `puff`, `crx3`, `run`), "attempted by the client in that order. If a pipeline fails, the client will attempt the next pipeline" (https://github.com/chromium/chromium/blob/main/docs/updater/protocol_4.md). The updater caches one item per app (`<appid>_<fp>`).
- **From-version policy.** Server-side and closed. No public source states how many prior fingerprints Google keeps diffs for. Treat "Chrome serves diffs from the last N versions" as unsourced.
- **Fallback.** Server omits the diff when no fingerprint matches; client tries diff, then full; failures reported via `diffresult`/`differrorcode`.
- **Hot path.** 1 POST (check) + 1 GET (payload) + 1 ping; +1 GET on diff failure. Note the server-side lookup by *client-reported base hash* is what lets the check and the patch selection share one round trip.

### 2.2 Firefox partial MARs / Balrog

- **Delta method.** Partial MAR = per-file patches + `updatev3.manifest`; before patching, the updater checks "expected size and CRC of the existing file"; mismatch -> "the update fails and we fall back to using a complete MAR" (https://firefox-source-docs.mozilla.org/toolkit/mozapps/update/docs/MarFiles.html). Patcher moved from mbsdiff to Zucchini (https://firefox-source-docs.mozilla.org/taskcluster/partials.html); measured gains: 69.0 -> 69.0.1 partial 5.17 MB -> 1.94 MB (-62.5%), 70.0 -> 70.0.1 5.54 -> 2.15 MB (https://bugzilla.mozilla.org/show_bug.cgi?id=1632374). Balrog example: complete 80,329,415 B vs partial 39,520,883 B (major bump), 138,485 B partial for 43.0.1 -> 43.0.2 (https://mozilla-balrog.readthedocs.io/en/latest/blob_examples.html).
- **Metadata.** Client GETs `update.xml` at a URL encoding product/version/buildID/target/locale/channel/OS (https://firefox-source-docs.mozilla.org/update-infrastructure/index.html). Balrog rules match on those fields; a release blob has `partials: [{from, filesize, hashValue}]`. Selection in `apprelease.py`: the requester's buildID must equal the `from` release's buildID for that target/locale, else the partial is dropped and only `<patch type="complete">` is emitted (https://raw.githubusercontent.com/mozilla-releng/balrog/main/src/auslib/blobs/apprelease.py).
- **From-version policy.** "The partial builds for RC1 should be (as of Firefox 63) the last 4 shipped releases on mozilla-release (plus the last beta for x.0 RCs)" (https://wiki.mozilla.org/Release_Management/Beta_Release_Checklist). Historically only the previous release until 2012; Firefox 15 added partials from 3 prior releases covering "more than 75% of the userbase" with the note "extra partials are far from free to generate" (https://bugzilla.mozilla.org/show_bug.cgi?id=575317). Watershed releases route stale clients through an intermediate version.
- **Hot path.** 2 GETs (update.xml, MAR via bouncer redirect); +1 MAR on partial failure. MAR container is signed; per-patch sha512 + size in update.xml.

### 2.3 Steam (SteamPipe)

- **Delta method.** "SteamPipe initially splits each file into roughly one megabyte (MB) chunks. Each chunk is then compressed and encrypted ... it searches to find any such chunks that match the previous build of the game, so ideally only the new or modified portions of any file are turned into 'new' chunks" (https://partner.steamgames.com/doc/sdk/uploading). Same doc warns that pack files with absolute-offset TOCs mean "even changing a few small assets in a pack file results in clients needing to download over half the entire file" - the fixed-offset-shift problem in a different costume. Manifest (reverse-engineered, SteamKit): per file, `ChunkData{ChunkID=SHA-1, Checksum=Adler32, Offset, CompressedLength, UncompressedLength}` (https://github.com/SteamRE/SteamKit/blob/master/SteamKit2/SteamKit2/Types/DepotManifest.cs). Chunk-to-chunk delta patches exist (`CContentDeltaChunks`, `patch_method` 1/2) but are undocumented by Valve (https://github.com/SteamRE/SteamKit/pull/616).
- **From-version policy.** Implicit: chunk identity by SHA-1 against whatever is on disk, so any prior build is a base.
- **Fallback / apply.** Missing chunks fetched whole; apply stages patched copies of every touched file and verifies before moving into place - a small download can rewrite gigabytes (user reports of a 483 MB patch taking ~3 h on a 101 GB install: https://steamcommunity.com/discussions/forum/0/3278065526397657828). No Valve statement was found for the rumoured 2023 "in-place chunk patching" change; treat as unverified.
- **Hot path.** App-info check + manifest request code (valid 15 min: https://steamdb.info/faq/) + manifest + one GET per missing chunk.

### 2.4 Debian debdelta

- Delta from old .deb to new .deb via xdelta/xdelta3/bsdiff, reconstructing the .deb "byte-by-byte identical" so APT signatures still verify; can use installed files as the base (https://manpages.debian.org/testing/debdelta/debdelta.1.en.html). Server: `debdeltas` computes deltas "from all --old versions to that version", `-n N` caps count; public service keeps deltas 50 days; Oct 2012 stats: "about 35% of requested deltas unavailable" (https://debdelta.debian.net/). Client probes the first kB of each delta, then flag files (`debdelta-too-big`, `debdelta-queued`, `debdelta-failed`) decide full vs delta (https://manpages.debian.org/testing/debdelta/debdelta-upgrade.1.en.html). dpkg team considers it "unnecessarily slow" because it re-tars/re-compresses (https://wiki.debian.org/Teams/Dpkg/Spec/DeltaDebs).

### 2.5 Fedora deltarpm and zchunk

- **deltarpm.** Reconstructs from installed files; `createrepo_c --num-deltas N` default 1, `--max-delta-rpm-size` 100,000,000 B (https://github.com/rpm-software-management/createrepo_c/wiki/dprms). dnf `deltarpm_percentage` = 75: "When the relative size of delta vs pkg is larger than this, delta is not used" (https://dnf.readthedocs.io/en/latest/conf_ref.html). Dropped in Fedora 40: over 42 upgrades "Delta RPMs were available for only 25 out of 42", "saved 7.5 MB / 8% of downloads on average", "wasted 52.7 MB of download on average (if there were failures)"; deltas were only available for ~a day because only one prior version was synced (https://fedoraproject.org/wiki/Changes/Drop_Delta_RPMs, https://lwn.net/Articles/925348/). This is the clearest published post-mortem of a K=1 patch-matrix policy: too few hits, expensive misses.
- **zchunk.** Rationale: casync needs "hundreds (and sometimes thousands) of individual HTTP requests"; zsync needs a separate index; so zchunk is self-describing (index in header) and "combine[s] range requests into one http request, a rarely used http feature ... the nginx default is 256 range requests in a single http request, while Apache's default is to support unlimited" (https://www.jdieter.net/posts/2018/05/31/what-is-zchunk/). Chunking: manual boundaries for XML, or buzhash CDC; chunks independently zstd-compressed with an optional shared dictionary that must be kept stable or "none of the chunks will match" (https://github.com/zchunk/zchunk). Format: lead -> preface -> index (per-chunk checksum/lengths) -> signature over header -> dict -> chunks; the index "is designed to be able to be extracted from the file on the server and downloaded separately" (https://github.com/zchunk/zchunk/blob/main/zchunk_format.txt). Measured: output ~23% larger than plain zstd, ~10% smaller than gzip; a 100 KB dictionary cut Fedora updates metadata "almost 40%" (https://www.jdieter.net/posts/2018/04/30/introducing-zchunk/). Fedora Change: daily users "should see a savings of up to 95%" (https://fedoraproject.org/wiki/Changes/Zchunk_Metadata). librepo client: range-GET header -> one multipart Range request for up to 256 missing ranges -> on a 200 instead of 206, halve `max_ranges` and retry -> eventually full-file GET (https://raw.githubusercontent.com/rpm-software-management/librepo/master/librepo/downloader.c). Broken-mirror multipart bugs did happen (https://github.com/zchunk/zchunk/issues/40).

### 2.6 ostree static deltas

- Baseline problem: archive repos need "one HTTP request per changed file"; Walters' 2013 design mail: a typo fix "still require[s] around 5 metadata HTTP requests, plus a redownload of the (gzip-compressed) file", large changes "thousands and thousands of HTTP requests", and servers must be "dumb content servers" (https://mail.gnome.org/archives/ostree-list/2013-July/msg00005.html). Foundries.io: a 750-file / 1.5 GB OTA becomes "38 files that are each about 30M" (https://foundries.io/insights/blog/ostree-static-deltas/).
- Format: `deltas/$fromprefix/$fromsuffix-$to` (modified base64 of commit hashes; no from-component for scratch deltas); `superblock` (metadata, timestamp, target commit object, recursive deltas, per-part sizes, fallback objects) + numbered parts = data blob + "a very restricted bytecode"; "The current delta compiler scans for files with matching basenames in each commit that have a similar size, and attempts a bsdiff between them"; "fallback objects" (e.g. initramfs) are fetched as plain `.filez` (https://ostreedev.github.io/ostree/formats/). Generator knobs: `--empty`, `--inline`, `--min-fallback-size` ("Minimum uncompressed size in megabytes for individual HTTP request"), `--max-chunk-size`, `--sign` (https://raw.githubusercontent.com/ostreedev/ostree/main/src/ostree/ot-builtin-static-delta.c).
- From policy: operator's choice; docs recommend parent and optionally `--from=ref^^`, plus `--empty` scratch deltas ("increased server disk space for fewer client HTTP requests"), and warn "Generating a full permutation of deltas across all prior versions can get expensive" (https://ostreedev.github.io/ostree/repository-management/). Flatpak: from-parent + from-empty only; a client "only ever downloads one static delta, the one named '$mylocalcommit-$latestremotecommit'" (https://blogs.gnome.org/alexl/2017/02/10/maintaining-a-flatpak-repository/). Foundries generates deltas from the versions the fleet actually runs (`fioctl targets static-deltas`).
- Client: `get_best_static_delta_start_for()` -> SCRATCH / FROM newest commit the client has / NO_MATCH -> per-object pull; 404 on superblock also falls back to per-object pull unless `require-static-deltas`. Deltas are named by (from,to) commit hashes so the client computes the URL with no lookup beyond the `summary`.

### 2.7 Android A/B OTA (update_engine)

- `payload.bin`: `"CrAU"` magic, manifest, manifest signature, blobs, payload signature; ops REPLACE/REPLACE_BZ/REPLACE_XZ, SOURCE_COPY, SOURCE_BSDIFF, PUFFDIFF, BROTLI_BSDIFF, ZUCCHINI, LZ4DIFF_*; each op carries `data_sha256_hash` and `src_sha256_hash`; per-partition old/new hashes (https://android.googlesource.com/platform/system/update_engine/+/refs/heads/main/update_metadata.proto).
- Source verification: "The hash of the source data on disk for this operation doesn't match the expected value. This could mean that the delta update payload was targeted for another version, or that the source partition was modified after it was installed" (https://android.googlesource.com/platform/system/update_engine/+/refs/heads/main/payload_consumer/partition_writer.cc); "when we detect a source hash mismatch, fail the OTA immediately and don't write anything" (https://android.googlesource.com/platform//system/update_engine/+/37b9b709252f6d2f0f0a8c4e3f453fad357a17a8). After apply, "the entire partition is re-read, hashed and compared". Chrome OS policy: "If it fails to apply a delta payload ... for a few times, it switches to full payload" (https://android.googlesource.com/platform/system/update_engine/+/refs/heads/main/README.md) - on Android that decision is the OEM's.
- From policy: one package per (source build, target build) via `ota_from_target_files -i`; AOSP has no policy.
- Streaming: the OTA zip is ZIP_STORED so entries are addressable by `name:offset:size`; the client fetches `payload_metadata.bin` by range first, verifies, then streams the body by range; "Steps 3 and 4 take most of the update time"; needs only "roughly 100 KiB of metadata" scratch (https://source.android.com/docs/core/ota/ab, https://android.googlesource.com/platform/build/+/refs/heads/main/tools/releasetools/ota_utils.py). Hot path: 1 check-in + 1 range GET (metadata) + 1 streamed range GET.

### 2.8 Windows Update: Full -> Express -> Delta -> forward/reverse differentials

- Sizes (Raymond Chen's series): Full/LCU "a little over 1 GB"; Delta (file-level, whole files) "typically around 300MB to 500MB", "cannot update customers who are more than one version behind"; Express "Each patch set is typically between 150MB to 200MB", client downloads "one seventh to a fifth" of Full, and "contains a Full update as an emergency fallback" (https://devblogs.microsoft.com/oldnewthing/20200211-00/?p=103430, https://devblogs.microsoft.com/oldnewthing/20200212-00/?p=103434).
- Express protocol: client downloads a stub, inventories local files, then "requests the WU client to download the ranges" in a loop; servers must support HTTP/1.1 partial ranges and keep-alive and must not use chunked encoding; proxies without range support "fall back to the full-file download" (https://learn.microsoft.com/en-us/windows-server/administration/windows-server-update-services/deploy/express-update-delivery-isv-support).
- UUP (since 1809): packages "contain forward differentials from quality update RTM baselines (ΔRTM→N) and reverse differentials back to RTM (ΔN→RTM) for each file that has changed since RTM"; client on N: V_N + Δ(N→RTM) = V_RTM, V_RTM + Δ(RTM→R) = V_R; "The endpoints retain the reverse differentials for the software revision they are on"; new files use "null differentials"; Express's stated failures: PSFs "can be large depending on the number of historical baselines", "only feasible to generate express download files for the most common baselines", and inventory is "expensive in terms of system memory utilization" (https://learn.microsoft.com/en-us/windows/deployment/update/forward-reverse-differentials). Chen: "roughly 250MB for the pair of patches", client download "less than double the size of an Express update download", "a 40% improvement in memory usage on the client" (https://devblogs.microsoft.com/oldnewthing/20200213-00/?p=103436/).
- Delta updates were retired 2019-02-12 because Express was smaller and did not require the prior month installed *(snippet of Mike Benson's 2018 post; original behind login)*.

### 2.9 Apple (brief; primary sources thin)

Standalone delta/combo macOS updaters ended with Big Sur (https://9to5mac.com/2020/12/17/no-delta-and-combo-macos-updates/) *(secondary)*. Rapid Security Response ships cryptexes with "both a patch and an antipatch" and applies "only to the latest minor operating system version" (https://support.apple.com/en-jo/guide/deployment/dep93ff7ea78/web) - a patch/antipatch pair is the same shape as UUP's forward/reverse pair, restricted to one base. iOS OTA assets list `PrerequisiteBuild`s *(community wiki, unverified)*.

### 2.10 Nix / Guix binary caches (no deltas)

- narinfo fields: `StorePath, URL, Compression, FileHash, FileSize, NarHash, NarSize, References, Deriver, Sig` (https://nix.dev/manual/nix/2.33/package-management/binary-cache-substituter.html). One GET per `.narinfo` per substituter, then one per NAR; Eelco 2012: "The main technical challenge ... is dealing with the latency involved in checking lots of remote .narinfo files. Nix uses persistent HTTP connections and lots of parallelism" (https://releases.nixos.org/nix-dev/2012-September/009826.html). Knobs: `narinfo-cache-positive-ttl` 2,592,000 s, `http-connections` 25, `max-substitution-jobs` 16 (https://nix.dev/manual/nix/latest/command-ref/conf-file). One datapoint: 802 narinfos over one connection "takes 11.8s with HTTP/1.1, but only 0.61s with HTTP/2" *(quoted on guix-devel: https://www.mail-archive.com/guix-devel@gnu.org/msg73631.html)*. Guix pipelines narinfo GETs ("only one round-trip to fetch 100s of narinfos").
- Delta attempts are all out-of-tree: casync-chunked NARs saved 48.47% on a mass rebuild but 1.07% on a Firefox bump (https://alternativebit.fr/posts/nixos/future-of-nix-substitution/); Attic dedups with FastCDC (min 256 KiB / avg 1 MiB / max 4 MiB, `nar-size-threshold` 8 MiB) (https://docs.attic.rs/admin-guide/deployment/nixos.html); nix-sandwich computes `zstd --patch-from`/xdelta3 deltas on demand against a heuristically chosen base: systemd 1,270,423 B vs 5,816,784 B xz, one system upgrade 71,381,554 B vs ~927 MiB (https://github.com/dnr/nix-sandwich). The `zstd --patch-from` result is directly relevant: LZ-with-old-as-dictionary is a cheap, streaming-decodable delta that Go can produce and apply today (`klauspost/compress/zstd` `WithEncoderDictRaw`/`WithDecoderDictRaw`, merged 2023-01-06: https://github.com/klauspost/compress/pull/728).

### 2.11 Docker/OCI layer distribution, partial pulls, layer deltas

- Cold pull round trips (verified live against Docker Hub): manifest GET -> 401 -> token GET -> manifest (index) -> platform manifest -> config blob -> each layer blob, where Hub/GHCR/Quay answer blob GETs with a 302/307 to a signed CDN URL, so 2 round trips per blob; ~7 requests for a 1-layer image. The spec makes the client the integrity check ("SHOULD verify that the response body matches the requested digest") and only "SHOULD support the Range request header" (https://github.com/opencontainers/distribution-spec/blob/main/spec.md). Tag -> manifest is the only mutable pointer; Hub serves it uncached with `ETag` = digest, so `If-None-Match` is a cheap poll; blobs sit behind CloudFront/Fastly/Akamai (Quay's redirect carries `cache-control: max-age=31536000`).
- Lazy pulling: Slacker (FAST'16): "pulling packages accounts for 76% of container start time, but only 6.4% of that data is read" (https://research.cs.wisc.edu/wind/Publications/slacker-fast16.pdf). CRFS/stargz (archived 2026-03): gzip member per entry, 4 MiB splits, TOC located via a 47-byte footer -> "1-2 HTTP requests" per layer, no per-chunk digests (https://github.com/google/crfs). eStargz: 51-byte footer, TOC digest bound to the manifest annotation, per-chunk `chunkDigest`, prefetch region "by a single HTTP Range Request"; Go library `github.com/containerd/stargz-snapshotter/estargz` (https://github.com/containerd/stargz-snapshotter/blob/main/docs/estargz.md). zstd:chunked: rollsum CDC with `RollsumBits = 16` (~64 KiB), TOC + tar-split in zstd skippable frames, TOC position in a manifest annotation so "we can avoid a round-trip"; missing chunks merged (up to `maxNumberMissingChunks = 1024`) into **one multi-range GET**, halving on `ErrBadRequest`, splitting a `200` client-side, else `ErrFallbackToOrdinaryLayerDownload` (https://github.com/containers/storage/blob/main/docs/containers-storage-zstd-chunked.md). Registries backed by S3/MinIO answered multi-range with 200, making c/image "download the entire layer blob ... discarding ~99.9%" (https://github.com/containers/image/issues/2792). SOCI: separate zTOC per layer, 4 MiB spans, layers <10 MiB not indexed; v2 abandoned Referrers-API discovery because "the referrers API is a weak, mutable reference" (https://github.com/awslabs/soci-snapshotter). Nydus: fixed 1 MB chunks, sha256/blake3 per chunk, Rust daemon; Ant Group reports pull 4m15s -> 560 ms (https://www.cncf.io/blog/2023/05/01/ant-group-security-technologys-nydus-and-dragonfly-image-acceleration-practices/).
- Layer deltas: `containers/tar-diff` (Larsson) - Go library, ops `Data/Open/Copy/AddData/Seek`, bsdiff-style `AddData` within files, output byte-identical so DiffID verifies; UBI 8.0 -> 8.1 deltas ~5-10% of layer size (https://github.com/containers/tar-diff, https://blogs.gnome.org/alexl/2020/05/13/putting-container-updates-on-a-diet/). Served via a `_deltaindex` tag whose entries are annotated with target digest and from/to DiffIDs; Flatpak >= 1.8 consumes it; the podman/skopeo PR was closed unmerged over GC of orphaned deltas and the mutable index tag (https://github.com/flatpak/flatpak-oci-specs/blob/main/image-deltas.md, https://github.com/containers/image/pull/902). `containers/oci-delta` for bootc: Fedora 41 -> 42, 972 M -> 999 M image, 555 M delta (only 44% saved) (https://github.com/containers/oci-delta). Balena v3 deltas use `balena-os/librsync-go` over the whole rootfs; worst case "equal size to the Docker pull" (https://docs.balena.io/learn/deploy/delta/). No OCI spec-level delta type exists.

### 2.12 P2P fan-out (Murder, Facebook, Kraken, Dragonfly, Spegel)

- Twitter Murder (2010): BitTorrent with a tracker and one seeder; "40 minute deploy ... 12 seconds" *(TorrentFreak, secondary: https://torrentfreak.com/bittorrent-makes-twitters-server-deployment-75-faster-100716/)*; unmaintained (https://github.com/lg/murder). Facebook: "a few hundred MB to tens of thousands of machines in one minute" *(secondary)*.
- Uber Kraken: agents + origins (S3/GCS backend) + tracker building a "pseudo-random regular graph"; 3 GB image, 2,600 hosts, 300 MB/s cap: p50 10 s, p99 18 s, p99.9 22 s; production "20K 100MB-1G blobs in under 30 sec" (https://github.com/uber/kraken). Go, but an application, not a library; low activity.
- Dragonfly (CNCF graduated): centralized per-piece scheduler + seed peers; client now Rust; Kuaishou reports Harbor bandwidth -70% average (https://www.cncf.io/case-studies/kuaishou-technology/).
- Spegel: stateless DaemonSet, libp2p Kademlia DHT over containerd's content store, 20 ms lookup timeout then 404 -> containerd falls back upstream; Crusoe: 17 GB image on 56 nodes median 348 s -> 307 s (https://spegel.dev/docs/architecture/, https://www.crusoe.ai/resources/blog/faster-image-pulls-at-scale). None of these do sub-blob dedup; they move whole content-addressed blobs.

## 3. Transport and latency: object storage and SSH

### 3.1 Object storage GET latency, throughput, cost

- AWS: request-rate floor 3,500 PUT / 5,500 GET per prefix per second; "consistent small object latencies (and first-byte-out latencies for larger objects) of roughly 100–200 milliseconds" (https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance.html); "When you make smaller requests (for example, less than 512 KB), where median latencies are often in the tens of milliseconds range, a good guideline is to retry a GET or PUT operation after 2 seconds"; use a connection pool to avoid "TCP slow-start and Secure Sockets Layer (SSL) handshakes on each request"; for large objects "requesting specific byte ranges of the object or downloading individual parts of a multipart object simultaneously" (https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance-design-patterns.html). The 2019 whitepaper's concrete numbers: "byte ranges of an object at the granularity of 8–16 MB. Make one concurrent request for each 85–90 MB/s of desired network throughput" (https://d1.awsstatic.com/whitepapers/AmazonS3BestPractices.pdf).
- Durner, Leis, Neumann (VLDB 2023): S3 "median base latency as ~30 ms and the median data latency as ~20 ms/MiB"; per-request bandwidth "median performance stabilizes at 55-60 MiB/s ... no outlier lies above the large cluster at ~95 MiB/s"; "Sizes of 8 - 16 MiB are cost-throughput optimal"; "less than 5% have a first byte latency above 200ms"; "Downloading a 1 KiB object costs the same as a 1 TiB object, as long as only one HTTP request is issued" (https://www.vldb.org/pvldb/vol16/p2769-durner.pdf).
- Pricing: S3 PUT $0.005/1000, GET $0.0004/1000, egress $0.09/GB (https://aws.amazon.com/s3/pricing/); R2 Class A $4.50/M, Class B $0.36/M, zero egress, free tier 10 M Class B/month (https://developers.cloudflare.com/r2/pricing/); GCS Class A/B $0.005/$0.0004 per 1000 *(secondary)*. S3 Express One Zone: "consistent single-digit millisecond data access", zonal endpoint only, GET $0.00003/1000 plus $0.0006/GB retrieval (https://aws.amazon.com/blogs/aws/up-to-85-price-reductions-for-amazon-s3-express-one-zone/) - irrelevant for WAN targets.
- Multi-range: S3 "doesn't support retrieving multiple ranges of data per GET request" (https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetObject.html); GCS XML API "Multiple byte ranges in a single request are not accepted" (https://docs.cloud.google.com/storage/docs/xml-api/reference-headers); R2 undocumented; CloudFront accepts ascending non-overlapping multi-range (https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/RangeGETs.html). GHCR returned 501 to a 2-range request in a live test; Hub (CloudFront) and Quay (Akamai) returned 206 multipart.
- HTTP/2: S3 REST answers an h2 preface with 400 "First received frame was not SETTINGS" (https://github.com/aws/aws-sdk-java-v2/issues/4615); GCS "supports HTTP/1.1, HTTP/2, and HTTP/3" (https://docs.cloud.google.com/storage/docs/request-endpoints). On S3, N parallel ranges = N TCP+TLS connections.

### 3.2 Conditional requests and pointer atomicity

- `If-None-Match` -> "304 Not Modified"; `If-Match` -> "412 Precondition Failed" (https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetObject.html). "There is no additional charge for conditional reads, conditional writes or conditional deletes. You are only charged existing rates for the applicable requests, including for failed requests" (https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-requests.html).
- Strong read-after-write for new and overwritten objects since 2020-12-01 (https://aws.amazon.com/blogs/aws/amazon-s3-update-strong-read-after-write-consistency/). `If-None-Match` on PutObject/CompleteMultipartUpload since 2024-08-20 (https://aws.amazon.com/about-aws/whats-new/2024/08/amazon-s3-conditional-writes/); ETag `If-Match` on PUT since 2024-11-25 (https://aws.amazon.com/about-aws/whats-new/2024/11/amazon-s3-functionality-conditional-writes/). GCS: `x-goog-if-generation-match` (Google advises generation over ETag preconditions) (https://docs.cloud.google.com/storage/docs/request-preconditions). R2: If-Match/If-None-Match on GetObject, HeadObject and PutObject (https://developers.cloudflare.com/r2/api/s3/api/). Caveat: multipart-uploaded S3 objects have non-MD5 ETags; keep the pointer single-part.
- A CDN in front reintroduces staleness on the pointer; sigstore's TUF repo serves `timestamp.json` (447 bytes) with `Cache-Control: no-store` (live fetch of https://tuf-repo-cdn.sigstore.dev/timestamp.json). Cloudflare: `immutable` "has no effect on public caches like Cloudflare" - use `max-age`/`s-maxage` (https://developers.cloudflare.com/cache/concepts/cache-control/).

### 3.3 SSH / rsync push

- rsync semantics (https://download.samba.org/pub/rsync/rsync.1): `--inplace`: "In-use binaries cannot be updated (either the OS will prevent this from happening, or binaries that attempt to swap-in their data will misbehave or crash)"; default mode writes a temp file and renames. `--write-batch`/`--only-write-batch`/`--read-batch` make a one-to-many delta but "The read-batch option expects the destination tree that it is updating to be identical to the destination tree that was used to create the batch" and batch mode "always negotiates a choice based on old-school md5/md4/zlib" unless overridden. `--checksum-choice` `xxh128, xxh3, xxh64, md5, md4, sha1`; `--compress-choice` `zstd, lz4, zlibx, zlib`. Block size: `sum_sizes_sqroot` uses `BLOCK_SIZE` (700) for files <= 700*700 bytes, else ~sqrt(len) rounded to a multiple of 8, capped at `MAX_BLOCK_SIZE` = 1<<17 (128 KiB) - verified in https://raw.githubusercontent.com/RsyncProject/rsync/master/rsync.h; ~7 KB blocks for a 50 MB file.
- Why rsync loses on rebuilt binaries: Percival, "Naive Differences of Executable Code": "Adding or removing a small number of bytes of code or data will change the relative position of blocks of code ... a one-line source code patch in a 500kB executable could translate into a 50kB patch file"; Table 1 weighted means: bzip2 2.8x, Xdelta 5.2x, .RTPatch 10.2x, bsdiff 11.6x, Exediff 13.7x; FreeBSD 4.7 security-update corpus (36,397,575 B): Xdelta 3,288,540 B (11.0x) vs bsdiff 621,277 B (58.3x) (https://www.daemonology.net/papers/bsdiff.pdf). rsync's fixed-block matcher is coarser than Xdelta, so expect it at or below Xdelta. wharf's measured example: two 82 MiB builds -> rsync 33 MiB vs bsdiff 174 KiB (https://fasterthanli.me/articles/efficient-game-updates). No published rsync-vs-bsdiff measurement on Go binaries specifically was found.
- SSH cost: SSHv2 = TCP + version exchange + KEXINIT + KEXDH + NEWKEYS + SERVICE_REQUEST + USERAUTH (OpenSSH adds a `none` auth round trip) + channel open with flow-control negotiation; roughly 6-8 RTTs before a command's first byte (counted from Fig. 1 of the SSH3 paper: https://arxiv.org/pdf/2312.08396). `ControlMaster`/`ControlPersist` reduce later sessions to ~1 channel-open RTT (https://man.openbsd.org/ssh_config.5); sshd `MaxStartups` default `10:30:100` (https://man.openbsd.org/sshd_config.5). Ansible default forks 5, `ControlPersist=60s`; pssh default parallelism 32.
- Push throughput ceiling is the workstation uplink: 100 hosts x 50 MB = 5 GB leaves one NIC regardless of SSH parallelism.

### 3.4 Fan-out and CDN

- Cost scale: 1000 hosts polling `latest` every 60 s = 1.44 M requests/day ~ $0.58/day on S3; 1000 hosts x 50 MB = 50 GB egress ~ $4.50 on S3, $0 on R2. Below ~1000 hosts, cost is not the deciding factor; RTT budget and uplink are.
- CloudFront caches ranges per range and forwards misses (https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/RangeGETs.html); Cloudflare in front of R2 caches by extension only by default, 206 only if the origin sent Content-Length (https://developers.cloudflare.com/cache/concepts/default-cache-behavior/). Content-addressed blob names make any TTL safe; only the pointer needs `no-store` or a short TTL. CDN-hit TTFB numbers exist only from third-party probes (~20-35 ms) *(secondary)*.

## 4. Polling / notification and manifest formats

- **No object store has a watch primitive.** S3 event notifications go only to SNS/SQS/Lambda/EventBridge and are "designed to be delivered at least once. Typically, event notifications are delivered in seconds but can sometimes take a minute or longer" and "aren't guaranteed to arrive in the same order" (https://docs.aws.amazon.com/AmazonS3/latest/userguide/EventNotifications.html). GCS -> Pub/Sub only, unordered, "on the order of 0.1 seconds" added write latency (https://docs.cloud.google.com/storage/docs/pubsub-notifications). R2 -> Queues only (https://developers.cloudflare.com/r2/buckets/event-notifications/). So sub-second detection needs a push side-channel (SSH, NATS, tiny long-poll server) with conditional-GET polling as the safety net.
- **Hot-path GET counts by manifest style:**

| Manifest style | Check + fetch | Notes |
|---|---|---|
| single `latest` pointer object | 1 (304) + 1 patch | pointer must be `no-store` at CDN; ETag polling |
| TUF (root/timestamp/snapshot/targets) | 4 minimum + target | timestamp is the only unversioned file; sigstore: 7-day timestamp, snapshot expiring 2036 |
| Omaha / Chrome | 1 POST + 1 GET | server picks diff from client's `fp` in the same round trip |
| Sparkle appcast | 1 + 1 | `sparkle:deltaFrom` enclosures, `maxDeltas = 5` default, EdDSA per enclosure; any delta failure -> full (https://sparkle-project.org/documentation/delta-updates/) |
| electron-builder `latest.yml` + `.blockmap` | 1 + 1 blockmap + N ranges | Rabin CDC avg 16 KiB (min 8, max 32), BLAKE2b-18 per chunk; downloader issues one Range request per changed run by default (https://github.com/electron-userland/electron-builder/blob/master/packages/electron-updater/src/differentialDownloader/DifferentialDownloader.ts) - the anti-pattern at 100 ms RTT |
| Squirrel.Windows `RELEASES` | 1 + K delta nupkgs | picks deltas vs full "by calculating which one requires less total downloading" (https://github.com/Squirrel/Squirrel.Windows/blob/develop/docs/using/update-process.md) |
| go-selfupdate family | >= 1 GitHub API + asset + checksums | 60 req/h unauthenticated - unusable for a polling fleet |

- TUF's value is not the GET count but its threat model (rollback, freeze, mix-and-match via snapshot; offline root; online timestamp key "minimal" risk) and its **consistent-snapshot naming** (`<version>.<role>.json`, `<hash>.<target>`) which makes every object except `timestamp.json` immutable (https://theupdateframework.github.io/specification/latest/). ostree's `$(mbase64 $from)-$(mbase64 $to)` naming has the same property for deltas.
- Embedding the patch in the manifest: none of the surveyed systems do it for binaries; TUF forbids content in metadata. app-builder appends the blockmap to the installer with a 4-byte length trailer, which is the closest precedent for "one object, index at a known offset" (https://github.com/develar/app-builder/blob/master/pkg/blockmap/blockmap.go).

## 5. Skipped-release strategies: what is used and a decision framework

| Strategy | Used by | Artifacts per release | Bytes for a K-behind client | Failure/drift behaviour |
|---|---|---|---|---|
| (a) chain of incremental patches applied sequentially | Windows Delta (retired 2019), Squirrel deltas, RADS (Riot's old patcher, "up to 8 prior versions") | 1 | K patches, K applies, K round trips unless bundled | one bad link breaks the chain |
| (b) patches from each of last K versions | Firefox (K=4 + beta), Chrome (K undocumented), ostree/Foundries (fleet-driven), debdelta (all within 50 days), deltarpm (K=1) | K | 1 patch if within K, else full | miss rate is the killer: debdelta 35% unavailable, deltarpm hit 25/42 |
| (c) forward + reverse against a base | Windows UUP, Apple RSR patch/antipatch (single base) | 1 pair | 2 applies, 1 download | client must retain its reverse delta; new files need null diffs |
| (d) CDC chunk reuse | Steam, zchunk, casync/desync/bita, Riot, zstd:chunked, Attic | 1 chunked object | proportional to actual difference; but executables shift so chunk reuse is poor for the changed region (Steam's own warning about pack files) | any local state is a seed; no failure mode beyond "fetch more" |
| (e) full download | everything, as last resort | 1 | full | - |

Decision framework, in terms of a 30-100 MB Go binary with one-line deltas:

- **Storage cost is not the constraint**: a bsdiff-class patch for a one-line change is tens of KB to a few hundred KB (Firefox point releases 1.94-2.15 MB for a whole browser; Courgette 78 KB for Chrome). Even K=20 patches per release is under 10 MB.
- **Generation cost is**: bsdiff needs `max(17n, 9n+m)` memory and is O(n log n) in the suffix sort (https://www.daemonology.net/bsdiff/); Zucchini takes "15-20 min" for Chrome; wharf's partitioned bsdiff cut 14.84 s -> 2.84 s with 11 partitions. A K-wide matrix multiplies this by K on the release hot path, which is exactly the "new release build finished -> targets reloaded" latency go-binsync cares about. Windows' UUP argument was precisely that Express's per-baseline diffs were "only feasible ... for the most common baselines".
- **Miss cost is a full download** (~1 s+ at S3 single-connection rates for 50 MB, plus the RTTs). Fedora's deltarpm data shows a K=1 policy wastes more than it saves once misses and failed applies are counted.
- **The (c) model dominates (b) for a single-binary product**: one reverse+forward pair per release, generated once, gives O(1) generation cost and any-version coverage, at the price of two applies on the target and a base that must be periodically re-chosen (Windows re-bases at feature updates; go-binsync can re-base when the forward delta from base exceeds a threshold, and re-basing is just "ship a full object and start a new base").
- **(d) is the wrong primary delta for executables but the right transport shape**: chunk-level reuse means the *unchanged* 95% of the binary never crosses the wire and the target can verify per chunk; the *changed* region should still be a bsdiff/zstd-patch-from delta, not a chunk fetch. Riot's numbers show that the transport shape (few, parallel, contiguous requests) mattered more than bytes.

## 6. Integrity, signing, drift

- **Hash throughput** (single thread): BLAKE3 Rust AVX-512 6866 MiB/s vs SHA-256 (OpenSSL, no SHA-NI) 484 MiB/s, BLAKE2b 1312 (https://github.com/BLAKE3-team/BLAKE3-specs/blob/master/benchmarks/bar_chart.py); Go `crypto/sha256` uses SHA-NI since 1.21, "on the order of 3-4x" (https://go.dev/doc/go1.21); `lukechampine/blake3` 4034 MB/s AVX-512 / 2105 AVX2 / 491 pure Go at 64 KiB (https://github.com/lukechampine/blake3); `zeebo/blake3` 4.00 GB/s at 1 MiB (https://github.com/zeebo/blake3); xxh3 31.5 GB/s C reference (https://github.com/Cyan4973/xxHash), `zeebo/xxh3` 25-149 GB/s (https://github.com/zeebo/xxh3). The BLAKE3 README's "12x SHA-256" compares against a non-SHA-NI SHA-256; vs SHA-NI it is ~3-4x. For 100 MB: SHA-256 no-NI ~200 ms, SHA-NI ~50-70 ms, Go BLAKE3 ~25 ms, xxh3 <5 ms. No primary Go arm64 SHA-256 figure was found.
- **Signing.** minisign: Ed25519, `ED` prehashed mode = ed25519(BLAKE2b-512(data)), trusted comment covered by the global signature (https://jedisct1.github.io/minisign/) - the trusted comment is a natural carrier for `version=`/`target_hash=`. signify: same base64 layout; OpenBSD signs a checksum list, not packages, because the package data "contains too much data to atomically sign" (https://www.openbsd.org/papers/bsdcan-signify.html). sigstore bundles allow offline verification via the SET ("verify an element was added to the log without hitting the log") (https://docs.sigstore.dev/cosign/verifying/verify/); never put Fulcio/Rekor on the hot path. `inconshreveable/go-update` order: patch -> checksum result -> verify signature over checksum -> write `.new` -> rename target to `.old` -> rename `.new` in; it never hashes the base (https://github.com/inconshreveable/go-update/blob/master/apply.go).
- **Drift ("target doesn't match any known base").** Seed-based systems need no concept of it: rsync "will also function correctly and reasonably efficiently when the files are quite different" (https://rsync.samba.org/tech_report/node2.html); zsync rolls over any local file and fetches misses (http://zsync.moria.org.uk/paper/ch02s03.html); casync/desync/bita seed from any file and verify each chunk by strong hash. Exact-base patchers must precheck: Android `src_sha256_hash` per op and fail-fast; Firefox per-file size+CRC -> complete; Squirrel `.shasum`; wharf applies into a staging dir, verifies every output against the new signature, "If there is a hash mismatch, the staging folder can simply be erased", and repairs "wounds" by fetching whole files from a full archive (https://raw.githubusercontent.com/itchio/wharf-spec/master/algorithms/apply.md). Octodiff: any failure or delta >= 80% of the package -> full (https://octopus.com/docs/deployments/packages/delta-compression-for-package-transfers). bsdiff/bspatch themselves verify nothing.
- **Atomic swap.** `rename(2)`: "If newpath already exists, it will be atomically replaced, so that there is no point at which another process attempting to access newpath will find it missing"; ETXTBSY applies to `open` for write on a running image, not to rename (https://man7.org/linux/man-pages/man2/rename.2.html, https://man7.org/linux/man-pages/man2/open.2.html). go-update's two-rename dance leaves a window where the path is missing and exists for Windows; on Linux a single rename suffices. None of the surveyed Go libraries fsync before rename.

Observations: no Go deploy tool does deltas; wharf is the only Go library with the full sig/patch/verify/heal loop and a bsdiff second pass; its rediff design (ship a fast rsync patch immediately, replace with a bsdiff patch later) is a latency trick go-binsync could invert (ship the bsdiff-class patch for the hot pair only, chunk-fallback for everything else).

## 9. Implications for go-binsync

The target is one Go binary, 30-100 MB, typically a one-line change, on N hosts, over ~100 ms RTT to S3/GCS/R2 or over SSH, with end-to-end latency (build done -> every target reloaded) as the objective. The evidence above points to the following.

### 9.1 Release-manifest model

- **One tiny, mutable, `no-store` pointer object per channel** (`releases/<channel>/latest`), single-part PUT so the ETag is stable, updated with `If-Match` CAS (S3 since 2024-11; GCS generation preconditions; R2 If-Match). Targets poll it with `If-None-Match`; a 304 is 1 RTT warm (~130 ms at 100 ms RTT + 30 ms base), costs one GET-class request, zero egress. This is TUF's `timestamp.json` role and Docker Hub's tag manifest; sigstore ships exactly this shape at 447 bytes.
- **Everything else content-addressed and immutable**, named so the client can compute URLs without a lookup: `blobs/<target_hash>` (full binary, zstd, range-addressable) and `patches/<base_hash>-<target_hash>` (ostree naming). Serve with `Cache-Control: public, max-age=31536000` so a CDN or R2's cache collapses fan-out to one origin miss per object.
- **The pointer carries the whole decision**: `{version, target_hash, size, base_hash (immediately previous release), patch_size, full_url, signature}` plus, for the hot pair, the patch itself when it is small. The manifest-embeds-patch pattern has no production precedent for binaries, but the numbers justify it: a one-line change under a bsdiff-class or zstd-patch-from delta is tens to hundreds of KB (Courgette 78 KB for Chrome; Firefox point releases ~2 MB for a whole browser), and at ~20 ms/MiB on S3 an inline 200 KB patch adds ~4 ms to the pointer GET versus +1 RTT (~130 ms) for a second object. The cost is that every no-change poll after a release still returns 304, so the embedded bytes are only paid once per target per release. Put a size cap (e.g. 1-2 MB) above which the pointer references `patches/<base>-<target>` instead. Sign the pointer with minisign/Ed25519 (trusted comment carries `target_hash`), verify before touching anything.
- **Hot path for a target on the previous release: 1 conditional GET.** For a target K releases behind: 1 GET (pointer) + 1 GET (patch or full). Never HEAD-then-GET (4 RTT cold vs 3).

### 9.2 Transport shape

- **Pull from CAS, not push over SSH, for anything beyond a handful of hosts.** A cold SSH session is ~6-8 RTTs before rsync even negotiates; push throughput is capped by the workstation uplink; and rsync's ~7 KB blocks are the wrong delta for a rebuilt Go binary. SSH is still the right *notification* channel from a workstation (or NATS/webhook from CI): "poke the host, host pulls" is the hybrid every object store forces on you because none has a watch primitive and S3 events are "seconds ... sometimes a minute".
- **Single-range, few-request layout.** S3/GCS have no multi-range; zchunk's 256-ranges-per-request and zstd:chunked's 1024-chunk multipart tricks do not transfer. So the producer must make the patch one contiguous object (or one contiguous region of a bundle), and the full-binary fallback should be fetched as 8-16 MB parallel ranges over separate connections (S3 is HTTP/1.1 only; ~85-95 MB/s per connection), i.e. 3-6 ranges for a 50 MB binary.
- **A bundle object per release** (`releases/<version>.bundle` = index header + patch-from-previous + patch-from-base + full) is a reasonable alternative to separate objects: 1 GET with `Range` after the pointer told the client the offsets. It costs nothing extra on the pointer path and avoids a second object lookup on the K-behind path. The index-at-known-offset precedent is app-builder's blockmap trailer.

### 9.3 Skipped releases

- Adopt the **Windows UUP model** rather than a K-wide matrix: for each release publish (i) forward delta from the current *base* release, (ii) reverse delta from this release back to base (small, shipped with the release and retained on the target), and (iii) the hot-pair delta from the immediately previous release. A target K behind applies its retained reverse delta then the forward delta: 1 download, 2 applies, O(1) generation per release. Generation cost is what actually lands on the build->reload critical path (bsdiff `max(17n, 9n+m)` memory, Zucchini 15-20 min for Chrome), so computing one hot-pair patch plus one base pair beats Firefox's 5 patches per release. Re-base when the forward delta from base exceeds a threshold or on a schedule; a re-base is just a full object plus a new base id in the pointer.
- The deltarpm post-mortem (25/42 hits, 8% saved, 52.7 MB wasted per failure) is the argument against K=1-and-nothing-else; the UUP paper is the argument against K=5.
- Full download remains the terminal fallback and should be cheap to reach: hash the on-disk base once (cache it keyed by inode/mtime; SHA-256 without SHA-NI on 100 MB is ~200 ms, most of the budget), compare to the pointer's `base_hash`, and go straight to full on mismatch instead of attempting a patch (Android's fail-fast, not go-update's fail-late).

### 9.4 Drifted targets

- Drift = on-disk binary hash matches neither `base_hash` nor any retained reverse-delta base. Exact-base patchers cannot recover; seed-based ones can. The pragmatic design is layered: (1) exact-base patch if `base_hash` matches; (2) otherwise, if the full object is published chunked (CDC ~64 KiB with a chunk index in the bundle header, per Riot/bita/zstd:chunked), the target can reuse whatever chunks it has and fetch only missing ones - but because S3/GCS are single-range, coalesce aggressively and fall back to the full ranged download above a small number of runs; (3) otherwise full download. Verify `target_hash` on the reconstructed bytes (BLAKE3 or SHA-NI SHA-256), fsync, single `rename(2)`, then re-exec/restart.
- Keep chunk reuse as an optimization for the unchanged 95% of the binary, not as the delta for the changed 5%: Steam's own docs describe how offset shifts defeat chunk reuse, and the bsdiff paper quantifies why.

### 9.5 What not to copy

- electron-builder's one-Range-request-per-changed-run (dozens of RTTs at 100 ms).
- casync/desync's one-GET-per-chunk store layout on object storage (hundreds of requests; zchunk was written specifically to escape this).
- TUF's 4-GET flow on the hot path; borrow its consistent-snapshot naming and its rollback/freeze checks (expiry timestamp + monotonically increasing version in the signed pointer) instead.
- rsync `--inplace` or scp over a running binary (ETXTBSY / "misbehave or crash").
- Online sigstore/Rekor verification on the hot path; verify bundles offline against a pinned key.

### 9.6 Open questions this research did not settle

- No published rsync-vs-bsdiff-vs-`zstd --patch-from` numbers exist for *Go* binaries specifically; the bench in `bench/` should produce them (bsdiff paper and wharf data are for C/Unity builds).
- Whether R2 supports multi-range GET (undocumented) and R2/CloudFront cache-hit TTFB from real target regions (only third-party probes exist).
- S3 event-notification latency distribution (only "seconds, sometimes a minute+" from AWS).
- Go arm64 SHA-256 throughput with SHA2 extensions (no primary figure found).
